1. 一张图看懂整条流水线

训练分两段：SFT 把群体分布吃进去，RL 用可验证奖励啃剩下的难例。 两段之间 SFT 的 checkpoint 兼做 RL 起点和 KL 参考——这一点省下的时间最多。

论文里的数字已经把话说死了：纯 RL 冷启 24.72%，光 SFT 35.14%，两段拼起来 39.58%。 跳过 SFT 直接 RL 基本等于自残；别省这一步。

2. 这条链路上真正要抠的 6 件事

每一件如果只做到 80% 都会在最终指标上扣两三个点；合起来就是 Customer-R1 从 7.32% 能拉到近 40% 的原因。

1

先把 action schema 写死

  • 每个 action 类型的必填字段一次性定完：click.element_name、input.element_name + text、terminate。字段没定义的动作，reward 就没法验证，RL 也无从学起。
  • 输出强制 rationale → action 的 JSON。rationale 让模型先说理由，相当于把 CoT 写进格式里；action 字段是 exact-match 的比对锚点。
  • click 这种大类要提前拆到子类级（论文拆了 13 个），后面 reward 加权、Fine-grained 评测都直接复用这份拆分。

底层逻辑：NextAct 是"属性全中才算对"，schema 不稳奖励信号就是噪声，RL 只会学到格式。

2

把数据先收拾干净再谈训练

  • 历史 trace 里缺 rationale 的样本占大头。直接丢会少一大半，论文的做法是用 Claude / GPT-4o 拿 "HTML + 真实 action" 反推一个合理 rationale 补进去——把它当作弱监督就够了。
  • HTML 太长塞不进上下文，粗暴 truncate 会把关键页面截掉。实操是"近几步保全量 HTML，远的只留 action + rationale"，整段压在 65k tokens 里。
  • click 占了 86%，input / purchase / terminate 加起来不到 14%。训练集一定要上采样稀有动作，否则模型会默认"看到什么都点"。
3

SFT 是 RL 的脚手架，不是可选项

  • Token-level CE 就行，没什么花活。Backbone 选 Qwen2.5-7B-Instruct-1M——3B 在 Session Outcome 上会直接崩成 3.97%，不是调参问题，是容量不够。
  • 训练参数可以照抄论文：AdamW, lr=1e-5, warmup=150, steps=2000, bs=64，不需要自己重新搜。
  • SFT 产出的 checkpoint 要留住：既是 RL 起跑点，也是 GRPO 里算 KL 的 π_ref。两件事同一个权重。
4

Reward 才是 RL 阶段唯一值得反复改的东西

R = w(â) · Raction  +  Rformat
  • Raction：action type 和所有必填字段必须全中才给 1，缺一不可。这是保证主指标有意义的唯一办法。
  • Rformat：JSON 校验过才给 1。别小看这一项，格式崩了 RL 会直接发散。
  • w(â)：按稀有度拉开权重。不加权的 RL 会秒退化成 "只做最常见的 click"，加权是把这件事从结构上堵住——下面这张表就是原论文的设置。
动作权重
正确 input（稀有 + 信息密集）2000
正确大多数 click 子类1000
正确 click: product_option10
正确 click: review / search（最高频）1

错误 click（SFT+RL 阶段）−1

5

GRPO 的关键不在公式，在 β

J(θ) = E[ (1/G) Σᵢ (1/|oᵢ|) Σₜ min(rᵢ,ₜ · Ãᵢ, clip(rᵢ,ₜ, 1−ε, 1+ε) · Ãᵢ) − β · DKL(πθ ‖ πref) ]
  • 每个 prompt 采 n 个 rollout，组内算相对优势 Ãᵢ——这是 GRPO 相对 PPO 最省事的一点，不用再养一个 value network。
  • 工程栈就用 VERL + Megatron，tensor parallel + context parallel + activation checkpoint 全开，8×8 A100 起步。2 epochs、bs=64 是个合理起点。
  • β 才是需要认真扫的：太小模型会跑偏 SFT 得到的合理分布（reward hacking），太大等于把 RL 退化回 SFT。建议在 0.01 ~ 0.05 之间扫 3 个点，看哪个在 NextAct 和 Format Valid 上都不掉。
6

错一次分析一次，不要堆着一起

每轮 GRPO 训完，先按 action 细粒度子类切一遍准确率，再按用户 archetype 切一遍，找掉分最狠的桶。

踩出来的错通常能归成这几类，对应修法基本是固定的：

错法下一轮怎么改
输出格式崩把 R_format 的罚项加重，同时在 SFT 数据里补一批 schema 对齐样本
action type 整个搞错SFT 语料按类做重采样，把稀有 type 往上拉到 20% 以上
type 对但 element_name 选错位HTML 表示要加强，比如补 DOM 层级、selector path，而不是继续调 reward
明明该出稀有动作但模型不敢出把该动作在 w(â) 里的权重再抬一档

下一轮的推进顺序是固定的：先 SFT 把新增/重采样的样本吃掉，再 GRPO 精调。别跳步。通常 2~3 轮就能收敛，之后继续训边际很小，该停就停。

3. 从 P0 到 P6 的跑法

不必把整条流程一次跑完。第一遍跑到 P2 有个数再说；P3 的错误分析做完，P4/P5 的改法自然就有了方向。

4. 评测指标与它们各自管什么

别只看一个 aggregate 数字，每个指标都在盯一种"退化方式"。

  1. NextAct Acc — 主指标，所有属性必须全中；调参只跟它对齐。
  2. Action Type Macro-F1 — 看模型有没有偷懒只做高频 click；这个指标掉了说明 reward 加权没起作用。
  3. Fine-grained Type Acc — 看 click 到子类是否分得清；跟 HTML 表示质量强相关。
  4. Session Outcome F1 — 看整段会话最后是下单还是终止；对 persona 和全局意图最敏感。
  5. Format Valid Rate — 本该稳定在 99% 以上；跌了说明格式 reward 或 KL 出了问题，先别看其它指标。
  6. Per-user Acc 分布 + Persona-swap — 1w persona 场景专门加的，防群体化坍缩；只看 aggregate 看不出来。
这套指标第一天就要全装上，不要后补。只盯 NextAct 调参的话，Macro-F1 和 Outcome 会悄悄掉，等发现就晚了。

5. 我踩过和看别人踩过的 3 个坑

① 省 SFT 这一步。 "反正 RL 会自己学出来吧"——不会。reward 在冷启阶段太稀疏，模型连格式都学不稳，loss 曲线会一直震。 Customer-R1 自己的数据：纯 RL 到顶 24.72%，而先 SFT 再 RL 拉到 39.58%，差的这 15 个点基本都是冷启损失的。
② 所有正确动作等权奖励。 看起来"公平"，结果模型会在 3 个 epoch 内退化成"狂点 review / search"——因为这两类高频动作的绝对正确次数最多，不加权的话总奖励最高。 必须按稀有度人为拉开：input = 2000、click review/search = 1，让模型发现去做稀有动作才更划算。
③ 纯 RL 阶段就放负奖励。 冷启时策略本来就抖，再给一个 −1 会让它直接发散；loss 一夜之间炸开。 负奖励只在 SFT+RL 联合阶段才打开——那时策略已经基本稳定，-1 能起到"修正边界"的作用而不是"砸锅"。
