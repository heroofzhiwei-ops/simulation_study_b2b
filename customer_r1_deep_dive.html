1. 一句话总结与速览

一句话：把 user persona 从 "prompt 里的装饰" 升级为 RL 真正要对齐的条件变量， 用 SFT 打底 + GRPO 微调、配 难度加权的可验证奖励，训出一个真正"像某个具体用户"而不是"像平均用户"的购物行为仿真 agent。
任务
在线购物中，给定 user persona 和会话历史，预测用户下一步动作（step-wise next-action prediction）。
Backbone
Qwen2.5-7B-Instruct-1M（长上下文版，65k tokens 上下文）。
训练方式
SFT → GRPO（RL），verifiable reward。
数据
OPeRA-filtered：49 个真实用户、5,856 条动作、207 条人工 rationale。
对比基线
Zero-shot / SFT / RL-only / SFT+RL（最优）。
核心收益
Next-Action 精确匹配 7.32% → 39.58%；Session Outcome F1 41.11% → 79.45%。

2. 问题定义：为什么已有方法不够用

过去三条线的购物行为仿真都存在一个共同盲点——只学"平均用户"的策略：

  • Generative Agents (Park 2023)：强调"可信"但没有定量对齐真实行为；
  • 早期 SFT 方法 (Lu 2025a)：在私有数据上做 supervised fine-tuning，不带 persona，复现性差；
  • Shop-R1 (Zhang 2025b)：引入 RL 提升动作准确率，但同样没有 persona 条件；
  • OPeRA (Wang 2025b)：把 persona 做进数据，但只做 prompting 评测，off-the-shelf 模型收益很小。
结果就是："同样的页面，不同的人会点不同的东西" 这个最关键的个性化维度，没有被任何工作真正训进 policy。Customer-R1 的问题动机正是填这个空。

3. 任务形式

3.1 输入与输出

一个购物会话 j，在第 t 步给定：

  • 历史动作 a₁, a₂, ..., a_{t-1}
  • 对应的 rationale r₁, r₂, ..., r_{t-1}（人工或合成的"为什么这样做"）
  • 页面 HTML 观测序列 o₁, o₂, ..., o_t
  • 用户 persona P_i（人口学 + 人格 + 购物偏好，来自问卷+访谈）

模型学习的函数：

rt, at = F( a1:t-1, r1:t-1, o1:t, Pi )

注意：先输出 rationale，再输出 action，整个是一个 JSON schema 结构化的单次生成。

3.2 Action Space（简化但覆盖电商骨架）

Action 类型必需属性示例占比
clickelement_nameclick on "filter_price"86.3%
inputelement_name, texttype "earbuds" into search box10.2%
terminate—结束会话（未购买）3.6%

click 的 13 种细粒度子类

review search product_option product_link purchase nav_bar page_related quantity suggested_term cart_side_bar cart_page_select filter other

细粒度类型后续在 reward 权重和评测里都会用到。

4. Customer-R1 框架

整个 pipeline 可以拆成三层。

4.1 输入层：Persona-grounded Prompting

  • 把 persona 描述 作为前缀 拼进 prompt，并在指令里要求模型"按 persona 行为"。
  • 关键工程细节：明确写 "若 persona 和当前页面证据/任务目标冲突，以后者为准"，防止模型只顾人设而忽略页面事实。
  • 长上下文处理：HTML 很长，他们做了动态截断——最近几步保留完整 HTML，早期步骤只保留 action + rationale，整体压到 65k tokens 之内。

4.2 训练层：GRPO 目标

用 DeepSeek 的 GRPO（不需要价值网络，用组内 rollout 的相对优势），目标函数是带 KL 正则的 clip objective：

  • 对每一步 prompt 采样 n 个 rollout，每个 rollout 的 reward 按下面的公式算，再转成组内相对优势。

4.3 输出层：Rationale-then-Action（JSON schema）

输出格式强制 "rationale 在前 + action 在后"，同时 rationale 不需要监督信号，只是 format reward 约束其存在。这等价于软性注入 CoT。

5. Reward 设计（论文的工程精华）

R = w(â) · Raction  +  Rformat

5.1 Action Reward（exact match，很严）

  • 只有当 action type 与所有必需属性都完全命中 时才给 1，否则 0。
  • 对 click：必须同时命中 type 和 element_name；对 input：type、area、text 全对才得分。

5.2 Format Reward

生成必须符合预定义 JSON schema（rationale + action），否则扣掉。

5.3 难度加权 w(â)：对抗类别不平衡

这是论文最值得借鉴的点。作者按动作的稀有度和信息密度拉开权重：

正确预测的动作权重（SFT+RL）备注
input（最稀少、最信息密集）2000文本输入，任务里最关键的行为之一
大多数 click 子类1000中等难度
click: product_option10中高频
click: review / search（最高频）1避免模型"什么都去点评论"
terminate1中性退出
错误的 click−1纯 RL 下会不稳，改为 0
直觉：如果把 review/search 的奖励也给到 1000，模型会退化成 "看见什么都去点评论"。把高频动作压到 1、稀有动作抬到 2000，强迫模型学什么时候该做那些稀有但关键的决定。 这是 class imbalance 场景下很通用的 reward shaping 思路。

7. 主结果与关键消融

7.1 主表（Table 4，%）

Method NextAct Acc Action Type Macro-F1 Fine-grained Acc Session Outcome F1

RL-only24.7231.1739.5840.51

  • 顺序：SFT+RL > SFT > RL-only > Zero-shot。
  • 纯 RL 冷启动只能做到 24.72%，说明奖励信号稀疏时必须 SFT 打底。
  • Zero-shot 仅 7.32%——这说明 购物行为预测是 pretrain 知识覆盖不到的任务。

7.2 Persona / Rationale 消融（Table 5，重点）

在 SFT+RL 下，把 persona 或 rationale 拿掉：

设置 NextAct Type Macro-F1 Fine-grained Outcome F1
SFT+RL（全量）39.5878.5061.2079.45
w/o persona37.8066.6759.4259.73
w/o rationale34.1573.1553.9967.37
Persona 的价值在哪？ 不在"下一步点哪里"的局部准确率（只掉 1.78 个点），而在 Macro-F1 掉 11.83、Session Outcome F1 掉 19.72——也就是 动作分布结构 和 最终是否下单。 这意味着：想做"像某个具体人"的仿真，persona 必须真的被训进 policy。
Rationale 是决策支架：去掉 rationale 在所有 setting 下都掉点，说明 "先写原因再写动作" 对把页面上下文和决策绑定起来很有帮助。

  • 3B：Session Outcome F1 直接崩到 3.97%，说明 "何时终止 / 何时下单" 这种全局决策对模型容量敏感，不是 7B 以下能撑起来的。

8. 论文的三句话精华

  1. 把 persona 从 prompt 装饰升级为 RL 真正优化的条件变量，才能产出个体差异化的仿真。
  2. 难度加权的 exact-match reward + 强制 JSON rationale-then-action 是把稀疏、长尾、多模态 HTML 场景跑稳 RL 的关键工程心法。
  3. SFT 打底 + GRPO 微调 是这类 agent 仿真目前性价比最高的 recipe；Zero-shot 和纯 RL 都不成立。

9. 局限与可被 claim 的改进点

  • 数据规模小：仅 49 个用户、5856 条动作、场景单一（Amazon）。若你能拿到真实分销者日志 + 店铺画像，体量上就能做 novelty。
  • 单用户 × 静态环境：没有 agent 间交互。B2B 分销天然是 "供应商 ↔ 分销者 ↔ C 端买家" 的多边博弈，是 Customer-R1 的超集。
  • 奖励只给 exact match：filter_price_asc 和 filter_price_desc 都是筛选，但 exact 只给一边。B2B 可以上 soft reward / LLM-as-judge。
  • Reward 权重手工拍：没有 adaptive curriculum。可引申为一个研究点：把难度权重学出来（RLAIF + meta-reward）。
  • Persona 文本静态：用户偏好随交互演化，可以做 动态 persona 更新（类似 Generative Agents 的记忆-反思机制）。

10. 对 1688→淘宝 B2B 分销仿真的直接启发

10.1 Persona 定义需要 B2B 化扩展

C 端 Customer-R1 的 persona 是 "人口学 + 人格 + 偏好"。B2B 分销者 persona 至少要覆盖：

  • 店铺规模、经营品类、历史毛利率偏好
  • 选品来源偏好（纯搬运 / 选品 / 自有供应链）
  • 风险偏好（库存 / 售后承受阈值）
  • 铺货节奏（搬运型 / 精选型 / 直播型）
  • 物流与合规敏感度（南北仓、报关、敏感词）
这样 agent 才会真正表现成："同一个 1688 商品页，A 分销者果断铺货、B 分销者直接划走"。

10.2 Action Space 要比 C 端大

类别建议动作
选品search_1688, filter_by_price, filter_by_ship_from, add_to_dist_pool
铺货list_to_taobao（含定价/标题/主图策略）, batch_relist
运营adjust_price, adjust_sku, delist, set_promotion
议价contact_supplier（多轮子任务：询价 / 起订量 / 账期）
履约accept_order, ship, handle_aftersale

建议沿用 Customer-R1 的 schema 风格：每个 action 定义必要属性 + 示例 + 允许出现的页面上下文。

10.3 Reward 直接套 "难度加权 exact match"

在你场景下，稀有但关键的动作（对标 Customer-R1 的 input）应该是：

  • 高权重（≈2000）：contact_supplier 的议价子任务、list_to_taobao 的定价动作
  • 中权重（≈1000）：大部分 adjust_*、add_to_dist_pool
  • 低权重（≈1）：翻页、浏览详情等高频低信息动作
  • 负奖励：价格倒挂、违规选品（若能用规则判定）

10.4 Rationale-then-Action 在 B2B 更好用

B2B 决策链条比 C 端长，rationale 能天然作为 "毛利估算 → 供应稳定性 → SKU 冲突判断" 的显性中间步骤。合成 rationale 直接用 claude-3.5-sonnet 或同级模型即可，和论文做法一致。

10.5 训练 Recipe 建议

  1. 数据：收集 N 名真实分销者的操作日志 + 店铺画像 + 访谈问卷，形成 persona 标注。
  2. SFT 预热：用 token-level CE 学习 "历史→动作" 的 base policy，至少覆盖高频动作。
  3. GRPO 精调：从 SFT checkpoint 起跑，用难度加权 exact match + format reward。
  4. 规模：7B + 65k context 是论文验证可行的最小规模；8×A100 起步。

10.6 评测口径迁移

论文的四个指标可以一对一映射：

Customer-R1→ 1688→淘宝分销
NextAct Exact Match下一步动作（含属性）命中率
Action Type Macro-F1分销动作类型分布一致性

10.7 可以直接成为一篇论文的切入点

  • 单体 → 多边市场：把 Customer-R1 扩展成 "分销者 × 1688 供应商 × 淘宝买家" 三方多 agent 仿真，研究补贴、协议变化的均衡效应。
  • 静态 → 动态 persona：让 persona 随交互更新，配合记忆/反思机制。
  • Exact → Semantic reward：引入 LLM-as-judge 给语义等价动作软奖励。
  • 行为 → 因果：结合 causal trace，做 "1688 选品 → 淘宝转化" 的端到端反事实评估。
